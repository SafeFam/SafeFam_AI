# Stacking 단독 운영 채택 기준

Issue #85 · LLM 없이 Stacking 모델만으로 운영하기 위한 승격 조건

이 문서는 기준을 **확정**한다. 이후 모델 버전은 모두 같은 기준으로 판정하며, 판정이 불리하다는 이유로 기준을 바꾸지 않는다. 기준 자체를 바꾸려면 6장의 절차를 따른다.

## 1. 판정 구조

단일 임계값 하나로는 피싱 Recall 확보와 정상 오탐 억제를 동시에 만족할 수 없다. 실제 문자 평가셋에서 Recall 0.95를 얻으려면 정상 다섯 건 중 하나를 오탐해야 한다.

그래서 경계를 둘로 나눈다.

| 구간 | 조건 | 사용자에게 |
|---|---|---|
| 확실 피싱 | `확률 >= phishing_min` | 자동 경고 |
| 의심 | 두 경계 사이 | 안내 문구를 동반한 소프트 경고 |
| 정상 | `확률 <= normal_max` | 알림 없음 |

두 목표가 서로 다른 경계로 옮겨가고, 그 사이 '의심' 구간이 충돌을 흡수한다. 따라서 **'의심' 구간의 크기도 기준에 포함해야 한다.** 그러지 않으면 모든 문자를 '의심'으로 밀어 넣어 나머지 기준을 형식적으로 통과할 수 있다.

## 2. 기준

`data_science/SMSModel/evaluation/adoption.py`의 `AdoptionCriteria`에 코드로 고정돼 있다.

| 항목 | 기준 | 근거 |
|---|---|---|
| 피싱 포착률 | **≥ 0.95** | 현행 하이브리드가 놓치는 피싱이 0건이다 (§2.3) |
| 자동 경고 오탐률 | **≤ 0.01** | 하루 정상 15건 기준 주 1회 오경보 (§2.1) |
| '의심' 정상 비율 | **≤ 0.133** | 하루 15건 기준 하루 2건 (§2.2) |
| P95 지연시간 | **≤ 50 ms** | 현행 10 ms 대비 여유. 배포 환경 vCPU로 측정 (§2.6) |
| 정상 표본 수 | **≥ 300** | 오탐 0건이 상한 1% 준수의 증거가 되려면 |
| 피싱 표본 수 | **≥ 60** | 놓침 0건이 상한 5% 준수의 증거가 되려면 |

### 2.1 자동 경고 오탐 상한 1%의 근거

사용자가 하루에 받는 정상 문자를 15건으로 본다.

| 오탐률 | 오경보 빈도 |
|---:|---|
| 5% | 주 5회 |
| 2% | 주 2회 |
| **1%** | **주 1회** |
| 0.5% | 2주 1회 |

자동 경고는 보호자에게 알림이 가는 동작이다. 오경보 한 건의 비용이 전화 한 통이므로, 주 1회가 신뢰를 잃지 않는 실질적 상한이다.

### 2.2 '의심' 정상 비율 상한의 근거

`#100`에서 재산정했다. 기존 0.10은 "하루 15건 기준 하루 1.5건"이라는 환산만 있고 왜 1.5건이 상한인지가 없었다.

'의심' 카드는 자동 경고와 성격이 다르다. 보호자에게 알림이 가지 않고 화면 안에 안내가 뜰 뿐이다. 오카드 한 건의 비용은 사용자가 문자를 한 번 더 확인하는 몇 초이며, 자동 경고의 전화 한 통보다 한 자릿수 낮다.

같은 방식으로 빈도를 환산한다.

| 비율 | 카드 빈도 | 판단 |
|---:|---|---|
| 6.7% | 하루 1건 | 비용 대비 과도하게 엄격 |
| 10% | 하루 1.5건 | 기존 값. 근거 없음 |
| **13.3%** | **하루 2건** | **채택** |
| 20% | 하루 3건 | 카드가 일상이 되어 읽히지 않는다 |

자동 경고를 주 1회(하루 0.14건)로 묶었으므로, 비용이 한 자릿수 낮은 카드는 하루 1~2건이 대응된다. **상한을 하루 2건으로 잡아 0.133으로 정한다.**

경보 피로가 실질적 한계다. 카드가 하루 3건을 넘으면 정상 문자에도 일상적으로 뜨는 것이 되어, 정작 피싱에 떴을 때 읽히지 않는다. 이 지점을 넘지 않는 선에서 가장 관대한 값을 택했다.

### 2.3 피싱 포착률 하한의 근거

`#100`에서 재산정했다. 기존 0.95는 유도 없이 값만 적혀 있었다.

`normal_max` 아래로 떨어진 문자는 '의심' 카드도 뜨지 않고 LLM으로도 넘어가지 않는다. 사용자에게 아무것도 보이지 않으므로, 이 비율은 곧 **제품이 그 문자에 대해 아무 일도 하지 않은 비율**이다.

기준점은 현행 제품이다. 단독 운영은 성능 개선이 아니라 LLM 의존 제거가 목적이므로, **현행 하이브리드보다 나빠지면 승격할 이유가 없다.**

| 구성 | 측정 recall | 놓친 피싱 |
|---|---:|---:|
| HYBRID (현행) | 1.0000 | 0건 / 75 |
| LLM_ONLY | 1.0000 | 0건 / 75 |
| SELF_MODEL_ONLY | 1.0000 | 0건 / 75 |

`reports/hybrid_evaluation/comparison_report.json` 기준이며, `sms_split_v1` 시절 test 126건에서 측정됐다. 단일 임계값 기준이고 판정셋도 다르므로 현행 밴드 지표와 직접 비교할 수는 없다. 다만 **현행 제품이 피싱을 사실상 놓치지 않는다**는 사실은 유효하다.

이 기준선에 비추면 0.95는 이미 관대한 값이다. 하이브리드가 0건을 놓치는데 단독 운영에 5%를 허용하는 것이므로, 완화할 근거가 없다.

**0.95를 유지한다.** 재산정 결과가 기존 값과 같다는 것 자체가 결론이다.

### 2.4 artifact 임계값 정책은 채택 기준과 다른 것을 잰다

`run_stacking_training.py`의 `TARGET_RECALL`과 `MAX_NORMAL_FALSE_POSITIVE_RATE`는 채택 기준과 같은 숫자(0.95, 0.01)를 쓰고 있었으나 **재는 대상이 다르다.**

| | 대상 | 측정 지점 |
|---|---|---|
| 채택 기준 | 2-임계값 밴드 | recall은 `normal_max`에서, 오탐은 `phishing_min`에서 — **서로 다른 지점** |
| artifact 정책 | 단일 임계값 | recall과 오탐을 **같은 지점**에서 |

밴드 구조를 도입한 이유가 두 지표를 서로 다른 지점에서 재기 위함이었다. 같은 숫자를 단일 임계값에 그대로 요구하면 밴드가 완화한 조건을 다시 묶는 셈이다.

더 큰 문제는 `0.01`이 **validation split에서 검증 불가능**하다는 점이다. validation 정상은 82건이므로 분해 가능한 최소 오탐률은 `1/82 = 0.0122`다. 0.01을 요구하면 실질적으로 "오탐 0건"이 되며, §2.5의 rule of three를 적용하면 0.01을 주장하려면 정상 표본이 300건 이상 있어야 한다. validation에는 82건뿐이다.

측정된 단일 임계값 절충이다.

| 오탐률 상한 | 허용 오탐 | 달성 가능 recall |
|---:|---:|---:|
| 0.01 | 0건 | 0.8085 |
| 0.02 | 1건 | 0.8298 |
| 0.05 | 4건 | 0.9362 |
| **0.10** | **8건** | **0.9574** |

`3/82 = 0.0366`이 82건에서 주장 가능한 하한이므로 0.01·0.02는 애초에 성립하지 않는다.

**artifact 임계값 정책을 `TARGET_RECALL` = 채택 기준의 피싱 포착률, `MAX_NORMAL_FALSE_POSITIVE_RATE` = 0.10으로 정한다.** 단일 임계값의 오탐은 사용자에게 직접 노출되지 않는다. 운영 라우팅은 `hybrid_policy.json`의 밴드가 결정하고, 사용자 대면 오탐 보장은 판정셋 308건에서 `alert_false_positive_rate`가 담당한다. 이 값은 artifact가 정책 경로에 저장될지를 가르는 provenance 표시다.

### 2.5 표본 수 요건

오탐률 상한을 **오탐 0건으로 확인**하려면 표본이 그만큼 있어야 한다. 관측 0건에서 95% 신뢰 상한은 대략 `3/n`이므로(rule of three), 상한 1%를 주장하려면 정상 표본이 300건 이상이어야 한다.

표본이 부족하면 통과도 미달도 아닌 **`INSUFFICIENT_EVIDENCE`** 로 판정한다. 이 구분이 없으면 데이터가 적을수록 기준을 통과하기 쉬워진다.

### 2.6 지연시간은 배포 환경의 vCPU로 잰다

`p95_latency_ms`는 측정 장비의 CPU 수에 좌우되는데, 기존에는 측정 조건을 남기지 않았다. 그 결과 개발 장비에서 잰 값이 그대로 판정에 쓰였다.

`#98`의 인코더를 같은 artifact로 두 조건에서 측정한 결과다.

| 측정 조건 | 파이프라인 p95 | 판정 |
|---|---:|---|
| 개발 장비 6스레드 | 38.22 ms | 통과 |
| **배포 환경 2 vCPU** | **54.89 ms** | **미달** |

배포 대상은 `t3.small`(2 vCPU / 2 GiB)이다. 같은 artifact가 측정 장비만 바꿔도 통과와 미달을 오간다.

인코더가 없는 v6를 같은 조건에서 재면 여유가 크다.

| artifact | 2 vCPU p95 | 판정 |
|---|---:|---|
| v6 (인코더 없음) | 11.65 ms | 통과 |
| v7 (인코더) | 54.89 ms | 미달 |

인코더는 `max_length`를 128로 줄여도 단독 p95가 36.15 ms라 예산을 맞추지 못한다. **현재 인프라에서 인코더는 배포할 수 없다.**

**지연시간은 배포 환경의 vCPU 수로 측정한다.** `run_adoption_gate`가 `latency_environment`에 `cpu_count`와 `OMP_NUM_THREADS`를 기록하므로, 판정 리포트만 보고도 어떤 조건에서 잰 값인지 확인할 수 있다.

측정 방법은 다음과 같다.

```
OMP_NUM_THREADS=<배포 vCPU> MKL_NUM_THREADS=<배포 vCPU> python -m data_science.SMSModel.run_adoption_gate
```

## 3. 판정 방법

- 판정은 **실제 문자 평가셋(`real_holdout`)으로만** 한다.
- 합성 셋(`synthetic_fp_stress`, `synthetic_new_holdout`)은 참고 기록에 남기고 **판정에 넣지 않는다.** 합성으로 판정하면 성능이 부풀려진다(`#83`).
- 구간 경계는 **validation에서만** 선정한다. 판정 split을 보고 경계를 재조정하지 않는다.
- 지연시간은 판정 split을 단건 추론해 측정한다.

```bash
python -m data_science.SMSModel.run_adoption_gate
```

결과는 `data_science/SMSModel/reports/adoption_gate.json`에 저장된다.

## 4. 판정 우선순위

| 상황 | 판정 |
|---|---|
| 확실한 미달이 하나라도 있음 | `FAIL` |
| 미달은 없으나 표본 부족 항목이 있음 | `INSUFFICIENT_EVIDENCE` |
| 모든 항목 충족 | `PASS` |

확실한 미달이 있으면 표본을 더 모아도 결론이 같으므로 `FAIL`이 우선한다.

Recall과 오탐률이 상충해 둘 다 만족할 수 없을 때는 **오탐 상한을 지킨다.** 오탐이 많은 알림은 사용자가 꺼버려서 Recall이 0이 되기 때문이다. 임계값 선정 단계에서 이미 강제되며(`ThresholdInfeasibleError`), 상한을 지키는 운영점이 없으면 학습이 중단된다.

## 5. 현행 판정 — v9

측정일 2026-08-23 · artifact `artifacts/stacking/v9-experiment` · 판정셋 387건(정상 304 + 피싱 83)

v9는 `#102`에서 base model을 파인튜닝 인코더로 교체하고 피싱 학습 데이터의 기관명 교체 아티팩트 22건을 제거한 결과다. 데이터셋이 바뀌어 판정셋이 391건에서 387건으로 줄었으므로, v7 이하와 비교할 때는 표본이 다르다는 점을 감안한다.

| 항목 | v6 | v7 | **v9** | 기준 | v9 판정 |
|---|---:|---:|---:|---:|---|
| 정상 표본 수 | 308 | 308 | 304 | ≥ 300 | 통과 |
| 피싱 표본 수 | 83 | 83 | 83 | ≥ 60 | 통과 |
| 피싱 포착률 | 0.8554 | 0.8795 | **0.9518** | ≥ 0.95 | **통과** |
| 자동 경고 오탐률 | 0.0000 | 0.0000 | 0.0066 | ≤ 0.01 | 통과 |

| P95 지연시간 | 11.65 ms | 54.89 ms | 측정 불가 | ≤ 50 ms | **판정 보류** |

### 종합: `FAIL` — 단독 운영으로 승격하지 않는다

### 5.1 피싱 포착률은 처음으로 통과했다

v7까지 미달이던 포착률이 0.8795에서 0.9518로 올라 처음 기준을 넘겼다. `#102`의 인코더 파인튜닝과 데이터 정리가 함께 작용한 결과다.

`'의심' 정상 비율`은 v7의 0.1201에서 0.1908로 나빠진 것처럼 보이지만, 두 지표는 **경계를 사이에 둔 트레이드오프**다. v7은 경계를 낮게 잡아 의심 구간을 좁힌 대신 피싱을 놓쳤고, v9는 포착률을 확보한 대가로 의심 구간이 넓어졌다. 한쪽만 떼어 비교하면 오해가 생긴다.

모델 자체의 실력은 임계값과 무관한 지표로 확인한다.

| 지표 | 파인튜닝 전 | v9 |
|---|---:|---:|
| ROC-AUC | 0.9621 | 0.9653 |
| PR-AUC | 0.9250 | **0.9448** |

### 5.2 유형별 오탐률은 전 구간에서 개선됐다

artifact 임계값 기준 real_holdout 정상 304건. 임계값이 0.1502에서 0.1638로 함께 바뀌었으므로 절대값이 아니라 개선 폭으로 읽는다.

| 정상 유형 | 파인튜닝 전 | v9 | 변화 |
|---|---:|---:|---:|
| 정상택배배송안내 | 78.6% | 32.1% | −46.4p |
| 정상금융알림 | 61.3% | 25.8% | −35.5p |
| 정상포인트소멸알림 | 52.2% | 17.4% | −34.8p |
| 정상광고프로모션 | 60.5% | 26.3% | −34.2p |
| 정상카드결제알림 | 63.0% | 29.6% | −33.3p |
| 정상공공기관알림 | 71.0% | 38.7% | −32.3p |
| 기타정상 | 45.5% | 15.2% | −30.3p |
| 정상인증알림 | 4.5% | 2.3% | −2.3p |
| 일상대화 | 2.0% | 6.1% | +4.1p |

전체 오탐률 43.8% → **19.7%**. 사용자 관점에서는 정상 304건 중 무언가 표시되는 문자가 133건에서 60건으로 줄었다.

### 5.3 미달 원인은 데이터다 — 임계값 정책도 모델도 아니다

`#102`에서 세 원인을 분리해 각각 실측으로 확인했다.

**임계값 정책이 아니다.** 경계(`normal_max`/`phishing_min`)를 조합해 훑어도 두 기준을 동시에 만족하는 지점이 **하나도 없다**. `normal_max`를 0.16에서 0.20으로 올리면 '의심' 비율은 기준에 근접하지만 포착률이 0.9277로 먼저 무너진다.

**모델이 아니다.** 다음 네 가지를 시도해 모두 실측으로 기각했다.

| 시도 | 결과 |
|---|---|
| OOF fold 5 → 10 | 경계가 0.0597 → 0.0655로 거의 안 움직임 |
| 기관 대조 신호를 메타 피처로 | 기관 언급이 정상 19.5% vs 피싱 14.7%로 방향이 반대 |
| 정상 데이터 중복 제거 | 0.1908 → 0.3684으로 **악화** |
| learning rate warmup/decay | 0.1908 → 0.2928로 **악화** |

정상 쪽 중복 제거가 악화된 이유는 기록해 둘 가치가 있다. 피싱에서는 같은 문자 9벌이 임계값 근처에 뭉쳐 recall 예산을 독식했지만, 정상에서는 `[삼성카드]/[현대카드]/[국민카드] 승인 45,000원...` 같은 변형이 **기관명이 무엇이든 이 템플릿은 정상**이라는 불변성을 가르치고 있었다. 같은 오염 패턴이라도 라벨에 따라 의미가 반대였다.

**데이터다.** 오탐이 남은 유형은 실수집 데이터가 거의 없다.

| 정상 유형 | 실데이터(`original`) | 합성·증강 | 실데이터 비율 | v9 오탐률 |
|---|---:|---:|---:|---:|
| 일상대화 | 136 | 3 | 98% | 6.1% |
| 기타정상 | 31 | 11 | 74% | 15.2% |
| 정상금융알림 | 23 | 18 | 56% | 25.8% |
| 정상공공기관알림 | 9 | 32 | 22% | 38.7% |
| 정상택배배송안내 | 18 | 77 | 19% | 32.1% |
| 정상카드결제알림 | 7 | 48 | 13% | 29.6% |
| 정상광고프로모션 | 14 | 112 | 11% | 26.3% |

**실데이터 비율과 오탐률이 그대로 역상관이다.** 학습 pool 정상 439건 중 262건(60%)이 증강 데이터이며, 출처별 난이도를 OOF로 재면 증강분이 실데이터보다 훨씬 쉽다(정상 평균 확률 `synthetic_normal_v3` 0.099 / `real_collected_v4` 0.073 vs `original` 0.142, 판정셋 0.179).

같은 이유로 **선정용 split도 만들 수 없다.** 임계값을 고르는 validation이 학습 pool에서 뽑히는데 그 60%가 쉬운 증강분이라, 7개 하이퍼파라미터 구성 전부에서 정상의 96.7~98.9%가 경계 아래로 내려가 변별이 안 됐다. 실제로 validation에서 가장 좋아 보이던 설정이 판정셋에서는 더 나빴다. `original`만으로 채우려 해도 실패 유형의 실데이터가 7~18건이라 유형 커버리지를 지킬 수 없다.

### 5.4 인코더를 뺀 구성은 미달 항목이 하나 더 늘어난다

인프라 부담 없이 데이터 정리분만 반영하는 안(NB + LR + SVM 3개)을 측정했다.

| 항목 | 파인튜닝 전 | 인코더 제외 | **v9(인코더)** | 기준 |
|---|---:|---:|---:|---:|
| '의심' 정상 비율 | 0.4342 | 0.3651 | **0.1908** | ≤ 0.133 |
| 자동 경고 오탐률 | 0.0033 | **0.0132** | 0.0066 | ≤ 0.01 |
| 피싱 포착률 | 0.9880 | 0.9518 | 0.9518 | ≥ 0.95 |
| 미달 항목 수 | 1 | **2** | 1 | |

개선의 28%만 데이터 정리 몫이고 **72%가 인코더 몫**이다. 인코더를 빼면 `자동 경고 오탐률`까지 기준을 넘겨 미달 항목이 둘로 는다.

### 5.5 인코더는 현재 인프라에 배포할 수 없다 — 판정 보류

v7에서 확인된 제약(§2.6)이 v9에도 그대로 적용된다. 파인튜닝은 forward 연산량을 바꾸지 않으므로 지연시간 특성이 v7과 같다.

| 항목 | 추가 부담 |
|---|---:|
| `torch` + `transformers` | +617 MB (배포 이미지) |
| 추론 메모리(RSS) | 605 MB |
| 2 vCPU P95 (v7 실측) | 54.89 ms (예산 50 ms 초과) |

배포 환경(`t3.small`)에 접근할 수 없어 v9의 P95를 §2.6 조건으로 측정하지 못했다. 개발 장비에서 `OMP_NUM_THREADS=2`로 재면 21.56 ms지만, 이는 애플 실리콘에서 스레드만 제한한 값이지 `t3.small` vCPU 성능이 아니다. v7도 같은 방식으로는 38.22 ms였으나 실제 배포 환경에서는 54.89 ms였다.

**따라서 지연시간은 통과로 기록하지 않고 판정 보류로 남긴다.** 배포 환경에서 재측정하기 전까지 이 항목은 미확정이다.

### 5.6 하이브리드에서의 실질 성과

단독 운영 승격과 별개로, 하이브리드에서 LLM에 넘기는 비율이 줄었다.

| | LLM 호출 비율 |
|---|---:|
| 파인튜닝 전 | 40.3% |
| 인코더 제외 | 31.3% |
| **v9** | **18.1%** |

판정셋 387건 기준 '확실한 정상' 172건 → 248건, '의심' 156건 → 70건이다. 이 수치는 채택 기준이 아니며 승격 근거로 쓰지 않는다. 다만 인코더 도입에 인프라 비용을 쓸지 판단할 때의 재료가 된다.

### 5.7 다음 조치 — 실수집 정상 문자 확보 (§6-3)

원인이 데이터이므로 수집 이슈로 분리한다. 필요한 것은 **정형 알림 형태의 실제 정상 문자**다.

| 유형 | 현재 실데이터 | 목표 | 우선순위 |
|---|---:|---:|---|
| 정상카드결제알림 | 7 | 50+ | 높음 |
| 정상공공기관알림 | 9 | 50+ | 높음 |
| 정상광고프로모션 | 14 | 50+ | 높음 |
| 정상택배배송안내 | 18 | 50+ | 중간 |
| 정상금융알림 | 23 | 50+ | 중간 |

일상대화는 실데이터 136건으로 오탐률이 6.1%다. 같은 수준의 실데이터가 쌓이면 나머지 유형도 같은 구간에 들어갈 것으로 본다.

**합성 데이터로는 대체할 수 없다.** 이미 `synthetic_normal_v3` 211건이 있으나 OOF 실측에서 실데이터보다 뚜렷하게 쉬웠고(정상 평균 확률 0.099 vs `original` 0.142, 판정셋 0.179), 오탐이 남은 유형은 정확히 합성 비율이 높은 유형이다. 생성 모델은 전형적인 문장을 만드는데, 실제로 어려운 문자는 비전형적이기 때문에 어렵다.

수집분은 **학습 pool과 선정용 split 양쪽에 필요하다.** 판정셋은 지금대로 두어야 이전 판정과 비교가 유지된다.

## 6. 기준 미달 시 절차

1. **승격하지 않는다.** 하이브리드(LLM 병행) 구성을 유지한다.
2. 미달 항목별로 원인을 분리한다 — 임계값 정책 / 모델 / 데이터.
3. 원인이 데이터면 수집 이슈로 분리하고, 수집 후 같은 게이트로 재판정한다.
4. 판정 결과를 이 문서 5장에 갱신하고, 이전 판정은 이력으로 남긴다.

기준값 자체를 바꾸려면 **판정을 실행하기 전에** 바꾸고, 근거를 2장에 남긴다. 미달을 확인한 뒤 기준을 낮추는 순서는 허용하지 않는다.
