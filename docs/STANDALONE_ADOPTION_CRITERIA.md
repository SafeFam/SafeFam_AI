# Stacking 단독 운영 채택 기준

Issue #85 · LLM 없이 Stacking 모델만으로 운영하기 위한 승격 조건

이 문서는 기준을 **확정**한다. 이후 모델 버전은 모두 같은 기준으로 판정하며, 판정이 불리하다는 이유로 기준을 바꾸지 않는다. 기준 자체를 바꾸려면 6장의 절차를 따른다.

## 1. 판정 구조

단일 임계값 하나로는 피싱 Recall 확보와 정상 오탐 억제를 동시에 만족할 수 없다. 실제 문자 평가셋에서 Recall 0.95를 얻으려면 정상 다섯 건 중 하나를 오탐해야 한다.

그래서 경계를 둘로 나눈다.

| 구간 | 조건 | 사용자에게 |
|---|---|---|
| 확실 피싱 | `확률 >= phishing_min` | 자동 경고 |
| 의심 | 두 경계 사이 | 안내 문구를 동반한 소프트 경고 |
| 정상 | `확률 <= normal_max` | 알림 없음 |

두 목표가 서로 다른 경계로 옮겨가고, 그 사이 '의심' 구간이 충돌을 흡수한다. 따라서 **'의심' 구간의 크기도 기준에 포함해야 한다.** 그러지 않으면 모든 문자를 '의심'으로 밀어 넣어 나머지 기준을 형식적으로 통과할 수 있다.

## 2. 기준

`data_science/SMSModel/evaluation/adoption.py`의 `AdoptionCriteria`에 코드로 고정돼 있다.

| 항목 | 기준 | 근거 |
|---|---|---|
| 피싱 포착률 | **≥ 0.95** | 최소 '의심' 이상으로 걸러낸 피싱 비율 |
| 자동 경고 오탐률 | **≤ 0.01** | 하루 정상 15건 기준 주 1회 오경보 |
| '의심' 정상 비율 | **≤ 0.10** | 하루 15건 기준 하루 1.5건 |
| P95 지연시간 | **≤ 50 ms** | 현행 10 ms 대비 여유. 회귀 감지용 |
| 정상 표본 수 | **≥ 300** | 오탐 0건이 상한 1% 준수의 증거가 되려면 |
| 피싱 표본 수 | **≥ 60** | 놓침 0건이 상한 5% 준수의 증거가 되려면 |

### 2.1 오탐 상한 1%의 근거

사용자가 하루에 받는 정상 문자를 15건으로 본다.

| 오탐률 | 오경보 빈도 |
|---:|---|
| 5% | 주 5회 |
| 2% | 주 2회 |
| **1%** | **주 1회** |
| 0.5% | 2주 1회 |

자동 경고는 보호자에게 알림이 가는 동작이다. 오경보 한 건의 비용이 전화 한 통이므로, 주 1회가 신뢰를 잃지 않는 실질적 상한이다. '의심' 카드는 안내에 그치므로 10%까지 허용한다.

### 2.2 표본 수 요건

오탐률 상한을 **오탐 0건으로 확인**하려면 표본이 그만큼 있어야 한다. 관측 0건에서 95% 신뢰 상한은 대략 `3/n`이므로(rule of three), 상한 1%를 주장하려면 정상 표본이 300건 이상이어야 한다.

표본이 부족하면 통과도 미달도 아닌 **`INSUFFICIENT_EVIDENCE`** 로 판정한다. 이 구분이 없으면 데이터가 적을수록 기준을 통과하기 쉬워진다.

## 3. 판정 방법

- 판정은 **실제 문자 평가셋(`real_holdout`)으로만** 한다.
- 합성 셋(`synthetic_fp_stress`, `synthetic_new_holdout`)은 참고 기록에 남기고 **판정에 넣지 않는다.** 합성으로 판정하면 성능이 부풀려진다(`#83`).
- 구간 경계는 **validation에서만** 선정한다. 판정 split을 보고 경계를 재조정하지 않는다.
- 지연시간은 판정 split을 단건 추론해 측정한다.

```bash
python -m data_science.SMSModel.run_adoption_gate
```

결과는 `data_science/SMSModel/reports/adoption_gate.json`에 저장된다.

## 4. 판정 우선순위

| 상황 | 판정 |
|---|---|
| 확실한 미달이 하나라도 있음 | `FAIL` |
| 미달은 없으나 표본 부족 항목이 있음 | `INSUFFICIENT_EVIDENCE` |
| 모든 항목 충족 | `PASS` |

확실한 미달이 있으면 표본을 더 모아도 결론이 같으므로 `FAIL`이 우선한다.

Recall과 오탐률이 상충해 둘 다 만족할 수 없을 때는 **오탐 상한을 지킨다.** 오탐이 많은 알림은 사용자가 꺼버려서 Recall이 0이 되기 때문이다. 임계값 선정 단계에서 이미 강제되며(`ThresholdInfeasibleError`), 상한을 지키는 운영점이 없으면 학습이 중단된다.

### 종합: `FAIL` — 단독 운영으로 승격하지 않는다

경계는 validation에서 `normal_max=0.1977`, `phishing_min=0.6386`으로 선정했다. 그 경계에서 validation 오탐은 0.000이었지만 실제 문자에서는 0.054로 벌어졌다. 분포 차이다.

**격차는 임계값 정책으로 메울 수 없다.** 확률 캘리브레이션도 답이 아니다. 경계를 순위로 고르기 때문에 단조 변환을 걸어도 구간 구성이 그대로다(`reports/calibration_analysis.json`).

남은 원인은 학습 데이터다. 오탐이 몰린 광고성 정상 문자는 실질 5종류뿐이며, 이 중 8건은 금액만 다른 같은 문장이다. 실제 문자 수집이 선행 조건이다(`docs/REAL_DATA_COLLECTION.md`).

## 6. 기준 미달 시 절차

1. **승격하지 않는다.** 하이브리드(LLM 병행) 구성을 유지한다.
2. 미달 항목별로 원인을 분리한다 — 임계값 정책 / 모델 / 데이터.
3. 원인이 데이터면 수집 이슈로 분리하고, 수집 후 같은 게이트로 재판정한다.
4. 판정 결과를 이 문서 5장에 갱신하고, 이전 판정은 이력으로 남긴다.

기준값 자체를 바꾸려면 **판정을 실행하기 전에** 바꾸고, 근거를 2장에 남긴다. 미달을 확인한 뒤 기준을 낮추는 순서는 허용하지 않는다.
