# 실수집 문자 보강과 v4 재학습 결과

Issue #89 · 실제 문자 수집 및 광고성 정상 데이터 보강

## 1. 목적과 결론

`#85`에서 v3를 판정한 결과 자동 경고 오탐률이 5.4%로 상한 1%를 넘었고, 원인은 학습 데이터로 지목됐다. 오탐이 몰린 광고성 정상 문자가 실질 5종류뿐이었기 때문이다.

실수집 문자 164건을 보강해 재학습했다. **자동 경고 오탐은 크게 줄었으나 피싱 포착률이 함께 떨어져 판정은 여전히 `FAIL`이다.** 원인은 데이터 부족이 아니라 **구조 특징 설계**로 확인됐다(4장).

## 2. 데이터 변화

`real_collected_v4` source로 164건이 순증했다. 166건 중 2건은 기존 데이터와 중복이었다.

split은 v4로 재생성했다. **평가셋(`real_holdout` 157건)은 손대지 않았으므로 v3와 v4를 같은 잣대로 비교할 수 있다.**

## 3. 판정 결과

artifact `artifacts/stacking/v4` · 판정 split `real_holdout`

| 항목 | v3 | **v4** | 기준 | 판정 |
|---|---:|---:|---:|---|
| 정상 표본 수 | 74 | 74 | ≥ 300 | 판정불가 |
| 피싱 표본 수 | 83 | 83 | ≥ 60 | 통과 |
| 피싱 포착률 | 0.8916 | **0.7831** | ≥ 0.95 | **미달** |
| 자동 경고 오탐률 | 0.0541 | **0.0135** | ≤ 0.01 | **미달** |
| '의심' 정상 비율 | 0.0676 | 0.0676 | ≤ 0.10 | 통과 |
| P95 지연시간 | 9.70 ms | 15.79 ms | ≤ 50 ms | 통과 |

### 종합: `FAIL` — 승격하지 않는다

자동 경고 오탐이 **5.4% → 1.35%로 4배 줄었다.** 오탐 4건이 1건이 됐고, 상한 1%(오탐 0건)에 한 건 차이로 못 미친다.

임계값 선정 단계에서도 개선이 보인다.

| | v3 | v4 |
|---|---:|---:|
| Recall 0.95에 필요한 FPR | 0.1406 | **0.0349** |
| FPR 1%에서 가능한 Recall | 0.638 | **0.750** |

다만 상한 1%로는 여전히 운영점이 없어 학습이 중단된다. artifact는 `--max-false-positive-rate 0.05`로 완화해 만든 **실험용**이며 단독 운영 후보가 아니다. 완화한 실행은 `artifacts/stacking/v4-experiment`에 저장되고 정규 경로 `v4`는 비어 있으며, 완화한 값은 metadata에 기록된다.

## 4. 미달 원인: 구조 특징이 희석됐다

같은 평가셋에서 v3와 v4를 비교하면 순위 품질 자체는 나아지지 않았다.

| real_holdout | v3 | v4 |
|---|---:|---:|
| ROC-AUC | 0.9367 | 0.9279 |
| FPR ≤ 2%에서 Recall | 0.566 | **0.675** |
| FPR ≤ 5%에서 Recall | 0.699 | 0.711 |
| FPR ≤ 10%에서 Recall | 0.819 | 0.807 |

낮은 오탐 구간은 좋아졌지만 전반은 제자리다. 피싱 포착률이 떨어진 이유는 **구조 특징 세 개의 판별력이 사라졌기 때문이다.**

피싱과 정상의 보유율 차이(클수록 판별에 유용):

| 특징 | 병합 전 | 병합 후 |
|---|---:|---:|
| `has_personal_info_request` | 0.031 | **-0.005** |
| `is_long_text` | 0.121 | **-0.002** |
| `has_account` | 0.045 | **-0.058** |
| `has_phone` | 0.018 | **-0.088** |

### 4.1 `has_personal_info_request`가 무력화됐다

`PERSONAL_INFO_PATTERN`은 `인증번호|비밀번호` 같은 **단어의 존재**만 본다. 요구하는 문장인지 알려주는 문장인지 구분하지 않는다.

정상 인증 문자는 정의상 이 단어를 포함한다.

```
[Web발신][배달의민족] 인증번호 [198788]를 입력해주세요.
```

수집분의 18.9%가 이 패턴에 걸리며, 정상 인증 문자 60건이 전부 `has_personal_info_request=1`이 됐다. 피싱 전용 신호로 만든 특징이 정상에서도 같은 비율로 켜지면서 판별력이 0이 됐다.

계정탈취형 피싱을 잡는 데 쓰이던 신호이므로, 포착률 하락과 방향이 맞는다.

### 4.2 `has_account`가 전화번호를 잡는다

`ACCOUNT_PATTERN`은 `\d{2,6}-\d{2,6}-\d{2,6}` 형태를 계좌번호로 본다. 전화번호 `02-345-6789`도 여기 걸린다.

수집분은 소상공인 광고라 연락처가 많아 41.5%가 이 패턴에 걸렸고, 계좌번호 신호가 정상 쪽으로 기울었다.

### 4.3 판단

**이건 데이터를 더 모아서 해결되는 문제가 아니다.** 정상 인증 문자를 넣는 순간 드러나는 특징 설계 문제이며, 수집을 계속하면 오히려 더 심해진다.

## 5. 다음 조치

1. **`PERSONAL_INFO_PATTERN`을 요구 표현으로 좁힌다** — `인증번호를 알려|불러|입력해 주시면` 처럼 제3자에게 전달을 요구하는 문형만 잡도록. 단어 존재만 보는 현재 방식은 정상 인증 문자와 구분할 수 없다.
2. **`ACCOUNT_PATTERN`에서 전화번호를 배제한다** — 지역번호·이동통신 접두사로 시작하는 형태를 제외한다.
3. 두 패턴을 고친 뒤 **재학습하고 같은 게이트로 재판정**한다. 특징값이 바뀌므로 artifact를 재사용할 수 없다.
4. 평가셋 정상은 여전히 74건이라 `normal_sample_size ≥ 300`은 미달이다. 판정을 `INSUFFICIENT_EVIDENCE` 밖으로 빼내려면 **평가셋용 실데이터가 별도로 필요하다.**

## 6. 남은 데이터 과제

- **URL이 부족하다.** 광고성 정상 145건 중 URL 포함이 12.4%다. 실제 광고는 링크가 흔하므로 "링크 = 피싱" 신호가 과하게 강화될 수 있다(`has_url` 대비 0.424 → 0.458).
- 수집분의 전화번호는 자릿수가 규칙적인 합성값이다. `normalize_text`가 `[PHONE]`으로 마스킹하므로 학습에는 영향이 없으나, 원문 그대로가 아님을 기록해 둔다.
